# deepmemory v2 方案（对话状态 · 分层记忆 · 按需召回）

> 版本：v2.1 讨论稿
> 状态：v2 主体已实现；v0.2.2 已收口任务/状态卡归属模型
> 更新：2026-08-17（北京时间）

## 1. 目标

deepmemory v2 不以“保存更多聊天”为目标，而是让记忆承担远距离历史上下文的连续性，同时保留最近原始对话对即时语义的作用。

核心目标：

1. 保存任务当前状态、执行过程、已确认决定和可追溯来源。
2. 普通问答先成为有时效的短期记忆，不污染长期活跃记忆。
3. AI 在自动注入不足时，可主动调用 `memory_recall` 搜索活跃、冷库、归档及来源原文。
4. 错误、争议、否决、已取代和敏感内容有明确状态与权限边界。
5. 状态卡和任务看板能跨会话恢复，并与 DeepSeek Harness 子 agent 编排对齐。
6. 重要阈值和评分权重尽量配置化；安全边界不可被普通配置绕过。

## 2. Preset 与模式边界

v2 使用不同的 DeepSeek Harness agent preset 承载不同运行边界，不在同一个 preset 内依赖运行时自动猜测模式。

当前规划三种 preset：

| Preset | 用途 | 默认能力 |
|---|---|---|
| `task` | 工作模式 | 完整工具、plan、子 agent、workflow、任务看板、任务过程记忆 |
| `daily` | 日常模式 | 轻量问答、复习、求教、日常状态卡和短期记忆 |
| `blank` | 第三方子插件模板 | 最小 Harness agent 骨架、插件挂载点、可配置预算；不预装 deepmemory 业务逻辑 |

三个 preset 可以共享同一个 memory-server 和持久化后端，但每个 preset 独立声明工具、状态卡投影、记忆注入范围和上下文预算。preset 只保存固定行为契约和能力组成，不保存某个会话的任务状态。

### 2.1 任务模式（`task` preset）

用于开发、部署、项目推进、持续规划和需要执行验证的工作。任务模式拥有对话状态卡、任务看板、过程记忆和子任务编排。

### 2.2 日常模式（`daily` preset）

作为普通问答、求教、临时查询和泛用对话的默认模式。日常模式拥有更容易变化的轻量状态卡，用于维持短期话题和临时事项，但不自动建立生活画像。

### 2.3 第三方子插件模板（`blank` preset）

仓库提供可复制、可修改的空白模板：`agent-preset/blank-template/`。

模板只包含：persona 和 agent instructions 的最小入口、可选工具的挂载位置、一个相对路径插件挂载点、preset 级上下文预算配置入口，以及关于 host plane、realm、工具 schema 和部署方式的注释。

模板不包含 deepmemory 的记忆注入、自动抽取、状态卡、任务看板、子 agent、workflow、Ralph 或外部编程 provider。

第三方开发者复制模板后，只需替换 preset 名称、persona、插件入口和工具组；自己的插件可以通过 Harness 运行时 API 接入服务，也可以把静态工具直接写进 preset。模板的预算配置只提供默认入口，不限制子插件自行定义更细的预算策略。

### 2.4 延后范围

生活模式与生活画像卡方案保留，包括当前状态、最近发生、当前牵挂、稳定偏好与边界、近期事项；本轮 v2 不实现，后续单独规划。

不新增独立学习模式。复习和求教属于日常模式，知识库只判断知识主题之间是否相关，不据此判断用户是否已经掌握。

## 3. 上下文与记忆的关系

记忆替代远距离、重复、低密度的历史上下文，不取代最近几轮原始对话。

每轮可用信息由以下部分组成：

```text
系统规则
+ 最近原始对话
+ 当前对话状态卡
+ 当前任务看板（任务模式）
+ 预算内自动注入的活跃记忆
+ AI 按需 memory_recall 调回的冷记忆、归档摘要或来源原文
```

自动注入与主动召回分离：自动注入只选择当前有效、高可信、非敏感且能帮助当前回答的内容；`memory_recall` 负责在细节不足时逐层深挖。

最近原始消息直接使用 Harness session surface，不由 deepmemory 复制一份。其余远距离信息由状态卡、任务看板摘要和记忆按预算补全。

## 4. 信息载体及职责

| 载体 | 负责什么 | 不负责什么 |
|---|---|---|
| 最近上下文 | 即时指代、语气、刚刚提出的限制 | 长期保存 |
| 对话状态卡 | 当前会话此刻的目标、焦点、缺口和下一步 | 完整历史、完整任务集合 |
| 任务看板 | 主任务及子任务的生命周期 | 工具原始输出 |
| 长期语义记忆 | 稳定偏好、约束、已确认决定、长期事实 | 临时问答、未确认候选方案 |
| 短期记忆 | 临时问答、近期事件、被调回且有用的冷记忆 | 永久有效事实 |
| 过程记忆 | 做了什么、结果、失败点、关键产出 | 逐条复制所有日志 |
| 来源档案 | 原始消息、工具结果、Harness 轨迹 | 默认自动注入 |
| 冷记忆 | 过期但仍可快速调回的短期/过程记忆 | 普通自动注入 |
| 压缩归档 | 一年后按主题、任务和时间压缩的历史摘要 | 默认搜索和默认注入 |

## 5. 任务模式

### 5.1 对话状态卡

“工作区状态卡”改为“对话状态卡”。每个 Session 独立拥有一张 task/daily 状态卡；状态卡不绑定 Workspace，也不强制绑定 Task。主任务只是卡片可引用的业务内容，不再是卡片所有者。

状态卡字段：

- **目标**：当前主任务最终要达到的结果。
- **准备规划**：近期准备推进、但尚未形成详细做法的事项，允许少量并行。
- **下一步**：已经明确做法、依赖和完成标准，可以直接执行的动作，允许少量并行。
- **进行中**：已经开始的主线事项和子任务；阻塞作为进行中事项的标记，不设独立看板列。
- **缺少信息**：继续规划或执行所需但尚未获得的信息、权限、文件或选择。
- **待用户确认**：AI 无权自行决定的事项。
- **最近结果**：最近一轮经过主 agent 校验的完成、失败或验证结果。

状态卡只展示当前焦点，不重复保存完整任务集合。“准备规划”来自看板的待规划事项，“下一步”来自已经就绪的待办事项。

### 5.2 任务看板

任务看板采用五个状态：

```text
待规划 → 待办 → 进行中 → 已完成
                    └──→ 已失败
```

- `待规划`：方向存在，但做法、依赖或完成标准尚未明确。
- `待办`：已经规划完成、可以执行，但尚未开始。
- `进行中`：已经实际执行；可附加阻塞标记、阻塞原因和缺少条件。
- `已完成`：达到完成标准并通过必要验证。
- `已失败`：一次执行尝试没有达到目标，保留失败原因和证据。

已失败任务允许重新打开到待办或进行中，原失败记录、失败原因和重开原因不得覆盖。

### 5.3 主任务、子任务与会话

- 一个主会话通常承载一个主任务。
- 修 bug、资料查询、验证和局部实现属于主任务下的子任务，不创建临时会话卡。
- 可并行子任务交给 Harness 子 agent；`spawn` 用于独立执行，`fork` 用于带当前上下文分叉。
- 子 agent 保留独立执行轨迹，完成后提交结构化结果。
- 子 agent 的“完成”不能直接更新主状态；必须由主 agent 根据证据和完成标准校验后，才能更新状态卡、任务看板或长期记忆。
- 小型后续修复默认作为旧任务的关联子任务，不重开主任务；只有修复推翻原验收或影响主要目标时，才重开主任务。

任务看板绑定 Workspace；每个 Task 必须保存 `workspace_id` 和关联 `session_id`。同一工作区内，任务可改绑另一会话；任务卡可直接打开对应会话。状态卡始终跟随当前 Session，不因任务改绑而迁移。

正常并行由一个主会话编排子 agent 完成。多个独立会话修改同一工作区任务时，以 Task 版本号做乐观冲突检测；每个会话自己的状态卡独立版本化，不允许跨会话静默覆盖。

### 5.4 状态卡修订轨迹

状态卡保存当前快照，并为每轮 assistant 回复形成一个不可变修订版本。状态卡历史永久保留，体积较大的原始消息和工具结果只通过来源 ID 引用，不复制进修订记录。

每个修订至少包含：

- 修订 ID、父修订 ID、版本号。
- 修改字段及修改前后值或结构化 patch。
- 修改者：用户、主 agent 或系统。
- 修改原因和北京时间。
- 来源消息 ID、工具轨迹 ID、子 agent 轨迹 ID。
- 修改前后内容哈希。

恢复旧版本时生成一个新的恢复修订，不删除中间历史。

## 6. 日常模式

### 6.1 日常状态卡

日常状态卡比任务状态卡更容易随话题变化，但仍需保证短期问答和临时事项的连续性。

字段暂定：

- 当前话题。
- 当前意图。
- 正在回答的问题。
- 已知背景。
- 仍缺少的信息。
- 最近结论。
- 下一步或待继续内容。
- 最多 3 个暂挂话题。

暂挂话题只保存话题名称、停留位置、未回答问题、最近活跃时间和与当前话题的相关度。暂挂 24 小时后从状态卡移除，并结算为短期记忆。

### 6.2 话题切换与复习连续性

话题明显切换时，旧话题先降低前台权重；仍有关联、仍有未完成事项或知识库判断属于同一知识主题时，进入暂挂而非立即结算。

话题相关性综合：

- 语义相关。
- 实体、项目、课程或对象相关。
- 知识库中的主题、章节和前置关系。
- 是否服务于同一任务或未解决问题。
- 是否有“继续、刚才那个、上次”等明确回指。

知识库只判断主题相关性，不判断用户是否掌握。掌握状态不能因 AI 已经讲过而自动建立。

## 7. 记忆准入

系统每轮都可以分析，但不是每轮都生成长期记忆。内容应按影响分类进入正确载体。

### 7.1 进入长期语义记忆

- 用户明确要求记住。
- 稳定身份、偏好、边界和交流习惯。
- 已确认决定、约定和长期目标。
- 以后操作必须遵守的项目约束或安全规则。
- 已由工具、文件或日志验证且可复用的结论。
- 用户纠正过、以后不应重复犯的错误。

### 7.2 进入短期记忆

- 只是问了几句随后转移的话题。
- 临时问答、近期事件和可能再次提起的细节。
- 尚未形成长期价值的候选方案讨论。
- 被调回且实际帮助当前回答的冷记忆。

日常短期记忆活跃 7 天，任务过程记忆活跃 15 天，均可配置。

### 7.3 更新状态卡或看板

- 当前目标、准备规划、下一步、进行中、缺少信息或待确认发生变化。
- 任务从待规划流转到待办、进行中、已完成或已失败。
- 子 agent 结果经主 agent 校验并被采纳。

### 7.4 只进入过程或来源档案

- 实际执行的关键步骤、验证结果和失败原因进入过程记忆。
- 完整消息、命令、日志和工具结果进入来源档案。
- 大段原文不直接作为自动注入记忆。

### 7.5 不保存正文

- 用户明确说“不要记”。
- API Key、密码、Token、私钥等未经允许的敏感原文。
- 无意义噪声、重复日志和无法解释的模型猜测。

用户要求不记时，只保留不含正文、主题和摘要的审计记录。

## 8. 候选方案与决策状态

候选方案必须与已采纳决定分开：

| 状态 | 含义 |
|---|---|
| proposed | 已提出，尚未讨论充分 |
| exploring | 用户正在追问、比较或修改；追问不等于采纳 |
| pending | 信息基本明确，等待用户决定 |
| adopted | 用户明确同意，或明确要求按该方案执行 |
| rejected | 当前未采用，但不代表永远不可行 |
| superseded | 曾采用，后来被新方案取代 |
| invalid | 明确“以后这样做是错误的”；只能由用户指定 |

未确认候选方案进入看板“待规划”。用户明确下令执行可视为隐式采纳。

被否决方案作为短期记忆保留，之后进入冷库。第一次否决即降低主动推荐分，但不降低历史检索能力；再次被否决继续增加推荐惩罚。AI 无权根据否决次数自动标记 `invalid`。

## 9. 生命周期

```text
最近上下文
  ↓ 话题暂离前台
状态卡暂挂（最多 3 个，24 小时）
  ↓ 结算
短期活跃记忆（日常 7 天 / 任务过程 15 天）
  ↓ 到期
冷记忆（365 天）
  ↓ 到期
压缩归档（摘要可检索，原始来源可追溯）
```

### 9.1 冷记忆调回

普通检索先搜索活跃记忆。信息不足时，AI 可自主调用 `memory_recall` 搜索冷库；仍不足时继续搜索压缩归档和指定来源原文。

冷记忆只有在实际补足当前问题、被引用进回答、用于纠正判断或支撑行动时，才由 AI 恢复到短期活跃层。单纯被搜索到不算有用。

恢复后的记忆再次被提及或再次有效使用时可以提高权重。强化有类型软上限和绝对硬上限；稳定、反复验证的内容允许小幅超过类型软上限，但不能无限强化。

### 9.2 压缩归档

冷库保存一年后，按主题、任务、时间段和决策链压缩归档。归档保存：

- 压缩摘要和关键时间线。
- 最终结果、未决问题、被否决和被取代方案。
- 原始来源和 Harness 轨迹引用。

归档默认不参与自动注入；活跃区与冷库信息不足时，`memory_recall` 才逐级搜索。

## 10. 时间模型

系统统一按北京时间（`Asia/Shanghai`，`+08:00`）解析、保存和展示时间。

每条记忆支持：

- `occurred_at` 或 `occurred_from` / `occurred_to`：实际发生时间或区间。
- `mentioned_at`：用户提到这件事的消息时间。
- `recorded_at`：写入记忆时间。
- `updated_at`：最后修改时间。
- `last_confirmed_at`：最后确认时间。
- `last_recalled_at`：最后召回时间。
- `valid_from` / `valid_until`：事实有效范围。
- `expires_at`：进入下一生命周期层的时间。
- `time_raw`：原始表达，如“上周”“前阵子”。
- `time_precision` 和 `time_confidence`：时间精度及解析可信度。

“上周”等相对时间要结合消息时间加工为北京时间区间，同时保留原始表达。没有明确事件时间时，按该轮对话消息时间填写事件时间，并标记为推定时间及较低时间置信度。

## 11. 争议、取代与错误

### 11.1 争议记忆

召回内容与当前对话、工具证据或其他高可信来源冲突时，标记 `disputed` 并在结果中提醒用户。争议记忆停止自动注入，但可由 `memory_recall` 查到。

用户确认后，系统根据确认结果修改、取代或恢复记忆，并写入修订轨迹。未获得确认时，AI 不得静默覆盖旧记忆。

### 11.2 已取代记忆

已确认的新事实替代旧事实时，旧条标记 `superseded`，停止普通检索和注入，但保留来源、替代关系和恢复能力。

### 11.3 用户指定无效

`invalid` 表示“以后再这样做就是错误的”，只能由用户明确指定。AI 可以提示当前证据不支持、执行失败或存在冲突，但不能自行永久判死方案。

## 12. 敏感信息

写入语义记忆、短期记忆、过程记忆和状态卡前，server 必须检测 API Key、访问令牌、密码、私钥和其他受保护内容。

- 原始敏感值不得进入普通记忆。
- 普通记录只保存脱敏占位符和命中审计。
- `memory_recall` 可提示存在相关受保护来源，但默认不展开原文。
- 敏感原文必须由当前用户确认后临时授权。
- 授权最多使用 3 次，并在 30 分钟或当前会话结束时失效，以先到者为准。
- 每次展开都记录审计，不将敏感原文重新写入普通记忆。

## 13. 检索与按需召回

检索不使用单一粗总分，分为四段：

1. **查询理解**：识别模式、意图、实体、时间范围、历史指代、所需证据和缺失槽位。
2. **硬约束过滤**：权限、作用域、模式、状态、敏感授权、时间范围和存储层级。
3. **多路候选召回**：向量、BM25、实体图谱、时间索引、任务关联、来源链、知识库主题关系和决策状态。
4. **分层精排与按需扩展**：先活跃概要，信息不足再扩展冷库、归档和来源原文。

### 13.1 评分维度

评分至少分为四组：

- **相关性**：语义、关键词、实体、知识主题、时间、任务、来源链和历史指代匹配。
- **有效性**：确认程度、证据强度、来源质量、有效状态、最后确认时间和冲突状态。
- **使用价值**：重要性、可行动性、连续性、信息增益、独有性和 token 成本。
- **生命周期调整**：新鲜度、冷库/归档惩罚、有效使用强化、否决惩罚和长期未确认惩罚。

记忆保留长期属性与动态属性：

- 长期属性：`importance`、`confidence`、`source_quality`、`confirmation_status`、`decision_status`、`actionability`、`reject_penalty`、`sensitivity_level`。
- 查询时动态计算：`relevance`、`time_match`、`recency`、`continuity`、`information_gain`、`token_cost`。

先通过有效性门槛，再比较相关性和使用价值；`invalid`、未授权敏感内容和不允许的作用域不能靠高分绕过硬约束。

### 13.2 结果充分性

返回数量不固定。系统先取小批候选，再判断关键槽位是否覆盖、是否存在高可信来源、是否有冲突、是否需要过程细节，以及当前证据是否足以支持回答。

自动注入、主动 recall、原文展开各自占上下文的具体比例和动态上限尚未确认，后续单独讨论。第一版实现不得把固定 Top-K 当作唯一控制手段。

## 14. 配置原则

可调参数尽量通过配置 schema 暴露，至少包括。预算属于 preset 级配置，`task`、`daily` 和 `blank` 可以分别覆盖默认值：

```yaml
topic:
  max_suspended: 3
  suspended_ttl_hours: 24
  relation_threshold: 0.60
  close_after_low_relation: 2
  protect_unfinished: true

lifecycle:
  daily_active_days: 7
  task_process_active_days: 15
  cold_retention_days: 365
  recalled_short_term_days: 7
  archive_compression: true

recall:
  active_first: true
  cold_on_insufficient: true
  archive_on_insufficient: true
  # 候选数量、结果数量和上下文占比待后续讨论

presets:
  task:
    budget_profile: task-default
  daily:
    budget_profile: daily-default
  blank:
    budget_profile: blank-default

sensitive:
  approval_required: true
  approval_max_uses: 3
  approval_ttl_minutes: 30

trace:
  card_history_enabled: true
  retain_revisions: true
  store_patch: true
  store_source_links: true
```

各评分维度和类型强化上下限也必须配置化。以下属于硬安全规则，不能由普通运行配置或模型自行绕过：

- `invalid` 只能由用户指定。
- 用户要求不记时不得保存正文、主题和摘要。
- 敏感原文未经用户授权不得展开。
- 子 agent 结果未经主 agent 校验不得成为主任务状态或长期决定。

## 15. P1 实施范围

P1 先打通 server 与 preset 插件主链，不做完整 UI 重构。

### 15.1 Server

- [ ] 建立任务、子任务、任务看板和对话状态卡数据模型。
- [ ] 建立状态卡当前快照、每轮修订、来源引用和版本冲突检测。

- [ ] 实现记忆准入、生命周期迁移、冷记忆恢复和类型强化上限。
- [ ] 实现敏感写入拦截、三次/30 分钟授权和展开审计。
- [ ] 实现分层检索骨架：查询理解、硬过滤、多路候选、精排和逐级扩展。
- [ ] 提供 `task`、`daily` 两套正式 preset 的差异化入口，以及 `blank-template` 第三方开发模板。
- [ ] 暴露任务、状态卡、记忆状态、生命周期、争议确认和 recall 所需 API。

### 15.2 Preset 插件

- [ ] 根据所选 preset 维护对应状态卡，不在运行时自动猜测 task/daily。
- [ ] 每轮回复结束生成一组过程概要并关联完整 Harness 轨迹；按准入规则决定是否持久化。
- [ ] 捕获主 agent 与子 agent 编排关系，子任务结果经主 agent 校验后回写。
- [ ] 按上下文预算组装状态卡、看板和活跃记忆；具体比例待后续确认。
- [ ] 增强 `memory_recall`，允许 AI 自主逐级搜索冷库、归档和来源原文。
- [ ] 增加争议提醒、用户确认更新和受保护来源授权流程。
- [ ] 保留 `memory_save`、`memory_briefing` 和受控 forget/失效操作。

### 15.3 验证

- [ ] 临时问答进入 7 天短期层，任务过程进入 15 天短期层。
- [ ] 暂挂话题最多 3 个、24 小时，复习相关主题不会被机械结算。
- [ ] 候选方案追问不变成 adopted；明确执行可变成 adopted。
- [ ] `invalid` 无法由 AI 自主设置。
- [ ] 冷记忆实际有用后恢复短期，再次有效使用时按类型封顶强化。
- [ ] disputed 停止自动注入，召回提醒并经用户确认后更新。
- [ ] 敏感原文授权最多 3 次，30 分钟或会话结束失效。
- [ ] 状态卡每轮一个修订，可比较、追溯和恢复。
- [ ] 子 agent 未经主 agent 校验的结论不能更新主任务。
- [ ] 时间相对表达转换为北京时间点或区间，并保留原始表达。
- [ ] 原有检索、图谱、备份、归档和配置能力无回归。

## 17. 开发纪律

- `bash scripts/verify.sh` 四层全绿后才允许部署。
- 部署只通过 `scripts/install.sh`，并保持幂等。
- `client.js` 修改走 HMR；preset 修改需要用户确认后再重启 dsh web。
- AstrBot 重启只使用 `astrbot restart`。
- preset `defineTool` 使用扁平 parameters；动态 Harness 插件使用 JSON Schema，两者不得混用。
- 重要性 `0.8+` 只用于目标、关键决定、稳定偏好和用户明确长期锚点。
- 生活画像、动态召回上下文占比和最终返回上限仍是待讨论项，不得在 P1 中擅自写死。

## 18. 下一轮讨论

下一轮优先讨论：

1. 总上下文如何在最近原文、状态卡、任务看板、自动记忆、主动 recall 和来源证据之间动态分配。
2. 不同查询类型下，记忆最多可占上下文的比例。
3. “信息已经足够”的判断条件和逐级扩展停止条件。
4. 返回结果的粒度：摘要、结构化事实、时间线、决策链、过程组和原文片段。
