# deepmemory 记忆面板重做方案（3 选 1）

- 日期：2026-10-21
- 目标：**首屏更快、第一眼更少**
- 被测对象：会话内「记忆」tab（`conversation.view` id=`memory`）+ 插件页「deepmemory 记忆」
- 代码：`/www/dsh/home/profiles/web/node_modules/dsh-deepmemory/client.js`（2078 行；`MemoryPanel` 在 1572–2078）

## 1. 现状实测（测试机 :6240，数据为生产克隆）

| 指标 | 实测 |
|---|---|
| `/v1/overview` 响应 | **108,944 B**，13 ms（`get_overview()` 硬编码 `LIMIT 300`，含每条 `content` 全文） |
| 首屏渲染的记忆行 | **300 行**，每行带展开原文/删除/改作用域/改域操作 |
| 首屏请求 | **串行** 3 个：`overview` → `cards/<kind>/<sid>` → `cards/.../revisions`；`context/injection` 并行 1 个 |
| 首屏区块数 | 9 块，全部展开：标题栏、状态卡、修订历史、会话维护（key/导出/清理）、手动写入、检索、全局列表、工作区/会话列表、统计 |
| `/v1/graph` | 140 KB / 277 ms（只在「图谱」子页加载，**不在首屏**） |
| client.js | 134,279 B / 2078 行 |

**结论**：慢的主因不在服务端（13 ms），而是 **300 行 × 全内容的一次性渲染 + 串行请求 + 9 块同屏**。优化点集中在客户端；服务端只需把 `overview` 的条数/字段变成参数。

## 2. 方案 A：极简首屏（状态卡 + 搜索 + 最近 10 条 + 三个入口）

```
┌ 记忆 ──────────────────────────────────────────┐
│ 目标：…                    [状态卡] [注入] [维护]│  ← 3 个入口按钮，不含正文
│ [ 搜索记忆… ]                        [搜索]      │
│ 最近 10 条（重要度 / 最近访问）                  │
│  • [42] 用户要求…                    展开 删除  │
│  …（每行 1 行摘要，点开才展开全文）              │
│ [查看全部 300 条 →]                             │
└─────────────────────────────────────────────────┘
```

- **首屏请求**：`overview?limit=10&fields=summary` + `cards/<kind>/<sid>`（只要 payload 摘要），2 个并行 → **≈8–12 KB**
- **信息架构**：记忆列表、会话维护、手动写入、注入详情、修订历史全部移到二级页（现有 `view` 机制已支持子页，只需新增 `all`/`maint` 两个视图）
- **服务端改动**：`get_overview(limit=300, fields='full')` 增加两个可选参数（默认行为不变，向后兼容）
- **工作量**：客户端中等（新增 2 个子页 + 折叠），服务端 ~10 行
- **风险**：低（纯渲染层 + 参数化；回退=换回旧 client.js）
- **效果**：首屏 DOM 从 ~3000 节点降到 ~120；请求从 4 串行 → 2 并行

## 3. 方案 B：三卡工作台（状态卡 / 任务 / 最近注入）

```
┌ 记忆 ──────────────────────────────────────────┐
│ ┌ 状态卡 ────────┐ ┌ 任务 (3) ──────┐          │
│ │ 目标/下一步 3 行 │ │ 进行中 2 待办 1 │          │
│ └────────────────┘ └────────────────┘          │
│ ┌ 最近注入 ─────────────────────────────────┐  │
│ │ 摘要 1 条 · 记忆 4 条 · 预算裁剪 0 字符     │  │
│ └───────────────────────────────────────────┘  │
│ [ 搜索 ] [全部记忆] [维护]                       │
└─────────────────────────────────────────────────┘
```

- **首屏请求**：`cards` + `tasks?limit=3` + `context/injection` 三路并行 → **≈10–15 KB**（`overview` 完全不拉）
- **服务端改动**：无新端点（`/v1/v2/tasks`、`context/injection` 已有）
- **工作量**：客户端中大（3 个新卡片组件 + 导航）
- **风险**：中（任务卡对非任务会话为空，需要空态；三卡仍可能被嫌多）
- **效果**：首屏信息密度最高但**分块清晰**；适合"一眼看会话在干什么"

## 4. 方案 C：渐进优化（最小改动，先止血）

保留现有布局，只做 5 件事：

1. 记忆列表默认 **10 条 + 「查看全部」**（展开后分页 50/页）
2. 状态卡、修订历史、会话维护、手动写入 **默认折叠**（标题栏点击展开）
3. `refresh()` **并行化**（`Promise.all`：overview / card / revisions）
4. 骨架屏 + 首屏 `initialLoaded` 前不渲染列表
5. `overview` 增加 `limit` 参数（服务端 1 行改动）

- **首屏请求**：同 A（10 条 ≈ 5 KB）
- **工作量**：最小（`MemoryPanel` 内改 + 服务端 1 行），**1–2 小时级**
- **风险**：最低（不改信息架构，出问题直接回退文件）
- **效果**：解决 80% 的"慢 + 信息多"，但布局仍是纵向 9 块（折叠后 ~4 块）

## 5. 对比与建议

| 维度 | A 极简 | B 三卡 | C 渐进 |
|---|---|---|---|
| 首屏体积 | 8–12 KB | 10–15 KB | 5–8 KB |
| 首屏 DOM | ~120 节点 | ~200 节点 | ~150 节点 |
| 首屏块数 | 4 | 4 | 4（折叠） |
| 工作量 | 中 | 中大 | **小** |
| 视觉改动 | 大 | 大 | 小 |
| 风险 | 低 | 中 | **最低** |

**建议**：**先做 C 止血（今天可完成）**，同时把 A 作为"第二批"（信息架构重排）；确认 A 的线框后再动。B 只在"任务/状态卡是你每天最常看的东西"时才值得。

- `client.js` 是 DSH 浏览器插件的 `__ModuleLoader__` 封装文件；改动后**刷新页面**即可验证，若被浏览器缓存则强刷；不需要重启 dsh-web（但如改了服务端需重启 memory-server）。
- 生产先改**测试机**（`/www/dsh-test-home/profiles/web/node_modules/dsh-deepmemory/client.js`），验证后同步生产。
- 任何服务端改动沿用现有 preflight：`node --check`（若改 JS）→ 重启 → 断言 `/v1/overview` 默认行为不变。
